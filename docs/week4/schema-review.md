# Week 4: Schema self-review

I reviewed the `schema.md` and ERD from part 2 with the questions in part 3. Each entry names the question that found the problem.

## Entry 1: Coverage (question 1)

**Works well:** Every requirement marked Stores data? = Yes has a home in the schema (FR-01 to FR-08 and FR-15 to FR-17 are mapped in 2a). The queue and a ticket's position are not stored. They are computed from `tickets`, so nothing has to be rewritten when someone joins or leaves.

**Problem:** `services.avg_minutes` is not needed by any requirement, and Jill's top task from her persona, knowing how long she will wait, is not in `requirements.md` at all. A column with no requirement means either a requirement is missing or the column is not needed. Found by question 1.

**Change:** I added a requirement for an estimated wait time on My place (Should, Stores data? Yes, because it uses `services.avg_minutes`). The estimate is people ahead × `avg_minutes`, computed when needed and never stored. I kept the column. The ERD and `schema.md` do not change.

## Entry 2: Double tap (question 4)

**Works well:** `tickets.id` is generated by the database, so two people can never get the same ticket number, even if they join at the same moment (NFR-02).

**Problem:** Nothing in the schema stops the same person from holding two active tickets for one service. A double tap on "Get my ticket", or a refresh after submitting, would create two waiting tickets. Jill would hold two places, and Isabella could call a ticket for someone who is already being served. Found by question 4.

**Change:** I kept the schema as it is for now. Before creating a ticket, the join route will check whether this person already has a waiting or called ticket for that service, and if so it will send them to that ticket instead of making a new one. This is enough for the app this week. A database rule that makes it impossible, instead of relying on the app, is something to add in a later week.

## Entry 3: Status and closed_at can disagree (questions 2 and 4)

**Works well:** The `status` CHECK allows only the five words the app uses, and the two time CHECKs stop a ticket from being called or closed before it was created.

**Problem:** "Is this ticket finished?" is stored twice, once in `status` and once in `closed_at`. They can disagree: a ticket could be `served` with `closed_at` empty, or `waiting` with `closed_at` filled. A daily report that counts closed tickets would then give a different answer from one that counts statuses. Found by question 2, and it is also bad data (question 4).

**Change:** I changed the `closed_at` row in the 2c table so that it must be empty exactly when the status is `waiting` or `called`, and filled for `served`, `no-show` and `left`. For FR-17 (undo a no-show), the app must clear `closed_at` at the same time as it sets the status back to `called`.

## Entry 4: Email as identity (questions 2 and 4)

**Works well:** `email` is `UNIQUE`, so a returning customer keeps one `users` row. The foreign keys use RESTRICT, so a user who has tickets cannot be deleted by mistake and old tickets stay available for reports (question 5).

**Problem:** The database accepts any text as an email, because the "@" check is only in Python. A typo creates a second user for the same person. Two people who share one email, such as family members, would also be merged into one row with only one name. Found by questions 2 and 4.

**Change:** I added `CHECK (email LIKE '%_@_%')` to the `users.email` row in the 2c table, so the database rejects values that do not look like an email. I kept email as the way to identify a person, because Jill's persona uses email. The known limit is that two people sharing an email share a `users` row, and the name from the latest visit is kept. I will revisit this if staff logins are added later.

## Questions with no problem found

- **Question 3 (facts, not results):** Nothing is stored that could be computed. Position, people ahead and the queue are all computed. `avg_minutes` is a setting, not a result.
- **Question 5 (deletes):** Both foreign keys use RESTRICT on purpose, because the bank needs old tickets for reports. A service is switched off with `is_active`, not deleted.
- **Question 6 (types):** Every moment in time is a `timestamptz`. True/false values use `boolean` and numbers use `integer`. Nothing that should be a number, a date or a true/false value is stored as text.
